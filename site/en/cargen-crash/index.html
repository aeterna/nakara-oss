CNetworkCarGenWorldStateData Pool Full: what works and what does not

A breakdown of the client-log spam and net.dll crash in FiveM OneSync: why the widely shared GAMECONFIG_FILE workaround does nothing, and how calling the native correctly guards against pool overflow without frameworks or configuration.

CNetworkCarGenWorldStateData Pool Full, Size == 100   (crash_hash net.dll+487A2)

The problem

CNetworkCarGenWorldStateData is a network pool with a fixed size of 100. On OneSync servers whose map has more than 100 vehicle generators (the game's ambient parked cars), the pool can fill up and the client logs the line above repeatedly. When it happens during a disconnect, an ordinary "connection lost" can escalate into a net.dll crash dump.

Why the popular GAMECONFIG_FILE overlay does nothing

A widely shared fix is a partial gameconfig overlay that claims to raise the pool from 100 to 1000:

data_file 'GAMECONFIG_FILE' 'gameconfig.meta'

It is a silent no-op. Every client logs this on connect, and the pool is never touched:

Could not add data_file resources:/<resource>/gameconfig.meta - invalid type GAMECONFIG_FILE

Why, checked against the CitizenFX source and the official references:

  • FiveM's LookupDataFileType (gta-streaming-five/src/LoadStreamingFile.cpp in citizenfx/fivem) resolves a data_file type by hashing the upper-cased name and matching it against the native RAGE data-file-type enum only. FiveM registers no GAMECONFIG_FILE type (a full-tree search of citizenfx/fivem finds none), and it is not in the data-files reference. The type is invalid on every game build, so no mounter is ever found.
  • CNetworkCarGenWorldStateData cannot be raised by any supported mechanism. It is not in the base common/data/gameconfig.xml <PoolSizes> (it is a hardcoded network world-state pool), and it is not on the increase_pool_size allow-list.

Because the pool size is fixed at 100, the only fix is to stop creating networked car-generator world state.

What the resource does

On spawn, and again every 5 seconds (the engine re-enables generators on zone changes and respawns), each client calls:

SetAllVehicleGeneratorsActiveInArea(<whole map>, false --[[bActive]], false --[[bNetworked]])

This disables vehicle generators (ambient parked cars) map-wide, locally, so no CNetworkCarGenWorldStateData is allocated. Player- and script-spawned vehicles (dealerships, garages, job vehicles) are not generators and are unaffected. When the resource stops it restores the vanilla (active) state, so a restart does not leave generators switched off.

It does not delete parked cars that already exist. If you want those gone too, do it in your traffic or density resource (for example SetParkedVehicleDensityMultiplierThisFrame(0.0) every frame).

The last argument is bNetworked, and it must stay false

This native has no "instantly" parameter. Passing true as the 8th argument publishes the change as network world state and allocates one CNetworkCarGenWorldStateData slot per call, so a call on a timer fills the 100-slot pool by itself and the fix becomes the bug.

This has happened: a version that passed true (with the parameter misnamed bInstantly in a comment) brought the Pool Full spam back, with the log lines spaced exactly at the re-assert interval. In client crash dumps, 1,270 Pool Full lines were observed, with 423 of them exactly 5,000 ms apart — the re-assert interval of a version that passed true. With false the call is purely local and the interval does not matter.

All on one live OneSync server, with the defaults in this repo:

Install

  1. Download nakara_cargen_fix-{{cargen.version}}.zip from the Releases page and verify it.
  2. Extract it into your resources/ folder so you have resources/nakara_cargen_fix/fxmanifest.lua.
  3. Add to server.cfg: 
    ensure nakara_cargen_fix
  4. Remove any data_file 'GAMECONFIG_FILE' overlay you added for this problem; it never worked.

Ensure order does not matter (this is not a boot-time gameconfig override). To check it on your server, drive through dense areas for about 15 minutes, die and respawn, and watch the client console (F8): there should be no CNetworkCarGenWorldStateData Pool Full line and no invalid type GAMECONFIG_FILE line.

To see whether your server suffers the vanilla overflow at all, use the client exports below for A/B testing (both are client-side and affect only the client that calls them — nothing is synced):

Export What it does
exports.nakara_cargen_fix:setRelief(false) restore vanilla generators and stop re-asserting — use it to reproduce the overflow as a baseline
exports.nakara_cargen_fix:setRelief(true) disable generators again immediately and resume the loop
exports.nakara_cargen_fix:isRelief() true while relief is active
