nakara_cargen_fix {{cargen.version}}

crash CNetworkCarGenWorldStateData Pool Full: อะไรได้ผล อะไรไม่ได้ผล

สรุปข้อเท็จจริงเกี่ยวกับปัญหา client-log spam และ net.dll crash ใน FiveM OneSync: ทำไมวิธีแก้ด้วย GAMECONFIG_FILE ที่นิยมแชร์กันถึงไม่ทำงาน และการเรียก native อย่างถูกต้องช่วยป้องกันการจัดสรร pool เกินได้อย่างไร โดยไม่ต้องพึ่ง framework และไม่ต้องตั้งค่าใดๆ

CNetworkCarGenWorldStateData Pool Full, Size == 100   (crash_hash net.dll+487A2)

ปัญหา

CNetworkCarGenWorldStateData เป็น network pool ที่มีขนาดคงที่ 100 ช่อง บนเซิร์ฟเวอร์ OneSync ที่แผนที่มี vehicle generators (รถ ambient ที่จอดอยู่ตามแมปของเกม) เกินกว่า 100 จุด ตัว pool สามารถเต็มได้ และ client จะบันทึก log ข้อความด้านบนซ้ำๆ อย่างต่อเนื่อง เมื่อเกิดขึ้นระหว่างที่ผู้เล่นหลุดจากการเชื่อมต่อ (disconnect) เหตุการณ์ connection lost ธรรมดาสามารถลุกลามจนกลายเป็น net.dll crash dump ได้

ทำไมวิธี GAMECONFIG_FILE ถึงไม่ได้ผล

วิธีแก้ปัญหาที่แชร์กันอย่างแพร่หลายคือการใส่ partial gameconfig overlay ที่อ้างว่าสามารถขยายขนาด pool จาก 100 เป็น 1000 ได้:

data_file 'GAMECONFIG_FILE' 'gameconfig.meta'

แต่ในความเป็นจริงมันไม่ทำงานเลย (silent no-op) ทุก client จะพ่นข้อความนี้ลง log เมื่อเชื่อมต่อ และขนาด pool ไม่เคยถูกแตะต้อง:

Could not add data_file resources:/<resource>/gameconfig.meta - invalid type GAMECONFIG_FILE

เหตุผลเมื่อตรวจสอบกับซอร์สโค้ดของ CitizenFX และเอกสารอ้างอิงทางการ:

  • ฟังก์ชัน LookupDataFileType (ไฟล์ gta-streaming-five/src/LoadStreamingFile.cpp ใน citizenfx/fivem) จะหาประเภท data_file โดยการ hash ชื่อที่เป็นตัวพิมพ์ใหญ่ แล้วเทียบกับ enum ประเภทไฟล์ดั้งเดิมของ RAGE เท่านั้น FiveM ไม่มีการลงทะเบียนประเภท GAMECONFIG_FILE ใดๆ (การค้นหาทั่วทั้งโค้ดของ citizenfx/fivem ไม่พบประเภทนี้) และไม่มีระบุไว้ใน data-files reference ประเภทนี้จึงใช้ไม่ได้บนทุก game build และไม่มี mounter ตัวใดมารองรับ
  • CNetworkCarGenWorldStateData ไม่สามารถขยายขนาดผ่านกลไกใดๆ ที่ระบบรองรับได้ มันไม่ได้อยู่ใน <PoolSizes> ของ common/data/gameconfig.xml ดั้งเดิม (เนื่องจากมันเป็น network world-state pool ที่ฮาร์ดโค้ดไว้) และไม่ได้อยู่ใน allow-list ของคำสั่ง increase_pool_size

เนื่องจากขนาด pool ถูกฟิกไว้ที่ 100 ทางเดียวในการรับมือคือต้องหยุดสร้าง networked car-generator world state

การทำงานของ nakara_cargen_fix

เมื่อผู้เล่นเกิด (spawn) และทำซ้ำทุกๆ 5 วินาที (เนื่องจาก engine ของเกมจะเปิดใช้งาน generator ใหม่อีกครั้งเมื่อผู้เล่นเปลี่ยนโซนหรือเกิดใหม่) แต่ละ client จะเรียกคำสั่ง native:

SetAllVehicleGeneratorsActiveInArea(<whole map>, false --[[bActive]], false --[[bNetworked]])

คำสั่งนี้จะปิดการทำงานของ vehicle generators (รถ ambient ที่จอดตามจุดต่างๆ) ทั่วทั้งแผนที่ในระดับเครื่องผู้เล่น (locally) ทำให้ไม่มีการจัดสรร CNetworkCarGenWorldStateData เกิดขึ้น ส่วนรถของผู้เล่นและรถที่เสกโดยสคริปต์ (ร้านขายรถ, โรงรถ, รถงาน) ไม่ใช่ vehicle generator จึงไม่ได้รับผลกระทบใดๆ เมื่อหยุด resource ตัวสคริปต์จะคืนค่ากลับสู่สถานะ vanilla ปกติ (เปิดใช้งาน generator) ทำให้การรีสตาร์ตไม่ทิ้งสถานะปิดค้างไว้

ตัว resource ไม่ได้ลบรถที่จอดอยู่แล้วในแมป หากต้องการนำรถเหล่านั้นออกด้วย ต้องดำเนินการใน resource จัดการ traffic หรือ density แยกต่างหาก (เช่น เรียก SetParkedVehicleDensityMultiplierThisFrame(0.0) ในทุก frame)

พารามิเตอร์สุดท้ายคือ bNetworked และต้องคงค่าเป็น false เท่านั้น

native นี้ไม่มีพารามิเตอร์ประเภท "instantly" การส่งค่า true ในอาร์กิวเมนต์ที่ 8 จะเผยแพร่การเปลี่ยนแปลงนั้นเป็น network world state และจัดสรรช่อง CNetworkCarGenWorldStateData เพิ่มหนึ่งช่องต่อการเรียกแต่ละครั้ง ดังนั้นการเรียกซ้ำตามเวลาจึงกลายเป็นการเติมเต็ม pool 100 ช่องจนล้นด้วยตัวมันเอง และตัวแก้นั่นเองที่กลายเป็นต้นเหตุของบั๊ก

สิ่งนี้เคยเกิดขึ้นจริง: เวอร์ชันที่ส่งค่า true (โดยเขียนกำกับในคอมเมนต์ผิดเป็น bInstantly) ทำให้เกิด Pool Full spam กลับมา โดยมีช่วงเวลาของ log ตรงกับรอบการ re-assert พอดี ใน client crash dump พบข้อความ Pool Full ถึง 1,270 บรรทัด และ 423 บรรทัดในนั้นมีระยะห่างกันเป๊ะที่ 5,000 ms แต่เมื่อส่ง false การเรียกจะเป็นการทำงานภายในเครื่องเท่านั้น และระยะห่างของรอบการเรียกจะไม่ส่งผลเสียต่อ pool

สิ่งที่เราตรวจสอบแล้ว

ข้อมูลทั้งหมดมาจากการทดสอบบน OneSync server จริงหนึ่งเครื่อง ด้วยค่าเริ่มต้นที่อยู่ใน repository นี้:

ข้ออ้างอิง หลักฐาน สถานะ
การส่ง bNetworked = true บน timer จะทำให้ pool เต็มด้วยตัวมันเอง client crash dump: พบข้อความ Pool Full 1,270 บรรทัด โดย 423 บรรทัดห่างกัน 5,000 ms พอดี ซึ่งตรงกับช่วง re-assert ของเวอร์ชันที่ส่ง true พบจริง (game build: Legacy)
resource นี้ (bNetworked = false) ไม่จัดสรรช่องใน pool busted spec ตรวจสอบการส่ง false แบบ literal ในทุกการเรียก; การทดสอบจริง 2.3 นาทีโดยเปิดการทำงาน (ต่อจากการรันแบบปิด 10.7 นาทีด้านล่าง) ไม่พบ Pool Full spec · การรันจริงช่วงสั้น (Enhanced / gen9)
data_file 'GAMECONFIG_FILE' ไม่ทำงาน (no-op) ซอร์สโค้ดของ CitizenFX และข้อความ log ใน client ตามด้านบน ตรวจสอบแล้ว (ทุก build)
การปิด generators ป้องกัน vanilla overflow ได้จริง การทดสอบ A/B เมื่อปิดการทำงาน: ขับรถ 10.7 นาที โดยมีรถจอดอยู่ ~80 คันในระยะ 150 ม. ผู้เล่น 1 คน — ไม่พบ Pool Full ปรากฏขึ้น จึงไม่มีอาการให้ป้องกัน ยังจำลองอาการไม่ได้ — Enhanced, 1 ผู้เล่น (ยังไม่ได้ทดสอบบน Legacy และ session ผู้เล่นหลายคน)

หากคุณสามารถจำลองอาการ vanilla overflow ได้ โปรดเปิด issue พร้อมระบุ game build, จำนวนผู้เล่น และผลการทดสอบ A/B จาก export ด้านล่างที่ GitHub Issues — นั่นคือหลักฐานส่วนที่เรายังต้องการ

วิธีติดตั้ง

  1. ดาวน์โหลด nakara_cargen_fix-{{cargen.version}}.zip จากหน้า Releases และตรวจสอบความถูกต้องของไฟล์
  2. แตกไฟล์ลงในโฟลเดอร์ resources/ เพื่อให้ได้โครงสร้าง resources/nakara_cargen_fix/fxmanifest.lua
  3. เพิ่มลงในไฟล์ server.cfg: 
    ensure nakara_cargen_fix
  4. ลบ overlay data_file 'GAMECONFIG_FILE' ใดๆ ที่เคยใส่ไว้แก้ปัญหานี้ออก เพราะมันไม่เคยทำงานได้จริง

ลำดับการ ensure ไม่สำคัญ (เนื่องจากไม่ใช่ boot-time gameconfig override) ในการตรวจสอบผลบนเซิร์ฟเวอร์ ให้ขับรถผ่านพื้นที่หนาแน่นประมาณ 15 นาที ลองตายแล้วเกิดใหม่ และสังเกต client console (F8): จะต้องไม่มีข้อความ CNetworkCarGenWorldStateData Pool Full และไม่มีข้อความ invalid type GAMECONFIG_FILE

หากต้องการตรวจสอบว่าเซิร์ฟเวอร์ของคุณพบปัญหา vanilla overflow หรือไม่ ให้ใช้ client exports สำหรับการทดสอบ A/B ดังนี้ (ทั้งสองคำสั่งทำงานฝั่ง client เท่านั้น และมีผลเฉพาะเครื่องที่เรียก):

Export การทำงาน
exports.nakara_cargen_fix:setRelief(false) คืนค่า vehicle generators แบบ vanilla และหยุดการ re-assert — ใช้เพื่อจำลองอาการ overflow สำหรับเทียบ baseline
exports.nakara_cargen_fix:setRelief(true) ปิด generators อีกครั้งทันทีและกลับมาทำงานตาม loop ปกติ
exports.nakara_cargen_fix:isRelief() คืนค่า true ขณะที่การป้องกันกำลังทำงานอยู่
